## 挂机聊天 rightchat 间距"调不动"排查（原始记录）

结论（给用户前先记下，避免下次重复考古）：

- 截图是挂机界面：`FightPointMapChatPanel` → `FightPointPassMainPanel.prefab` 的 `content/chat`，
  里面是 **`Fight/leftchat.prefab`(dc5c08d0) / `Fight/rightchat.prefab`(e81731b5)** 的实例。
  但工作区当时在改的是 `ChatPanel.prefab` 里 **`Chat/rightchat_prefab`(9014b405)** 的实例 override
  （m_Spacing 28.7 / Padding.Top / sizeDelta.y 178.7 / anchoredPosition -231…）——两套预制体互不影响。
- 真正的"运行时被改"机制：leftchat/rightchat 是 `chat` 条目 `VerticalLayoutGroup` 的子节点，
  uGUI 的 `LayoutGroup.SetChildAlongAxisWithScale` 每次 rebuild 都会把子节点
  `anchorMin/anchorMax` 强制成 (0,1)，并把 `anchoredPosition.x` 写成
  `pos + sizeDelta.x * pivot.x`（Child Control Width=off 只是不改宽，**位置照样被驱动**）。
  → 手改 anchoredPosition / 拖节点都不生效，只能改 Padding / Child Alignment / Pivot / 宽。
- `Fight/rightchat.prefab` 的 `bg` 上那个 VerticalLayoutGroup 是 **m_Enabled: 0**（left 是开的），
  所以 padL=196 / padR=51 完全不生效，气泡宽度被 LayoutElement 冻在 688.7。
- 代码里唯一硬写名字位置的是 `CountryFlagUtil.ApplyToChat`：`baseX = isMyChat and 0 or 1.1`，
  有旗时 ±52，每次绑定/刷新都覆盖，info_left/info_right 里排的 52 / -50.75 会被抹掉。

对称口径：可见边距 = 条目居中留白(45) + 该侧 root VLG padding(150)。
右边要镜像，需 `pivot.x=1`、宽 990、contentroot 宽 690、padR=150、align=UpperRight。

## 根因定案：rightchat 条目盒子高度塌成 0（2026-10-21 收尾）

前面四轮都在改 padding / spacing / 头像 y，方向是错的。用 Unity MCP 桥
（`.workbuddy/tools/unity_bridge.py codef`）把预制体实例化进 990 宽 Canvas、
`ForceRebuildLayoutImmediate` 后实测，才看到真因：

| | root h | contentroot h | bg h |
|---|---|---|---|
| leftchat | 161.2 | 136 | 136 |
| rightchat（修前） | **51.6** | **0** | 140 |

- `bg` 的 LayoutElement 写了 `m_IgnoreLayout: 1` → contentroot 的 VLG 整个跳过它
  → contentroot preferred height = 0 → 根 ContentSizeFitter 把条目压到 51.6。
- 挂机面板 `chat` 容器 VLG `spacing=43 / ChildControlHeight=1`，条目高度由各自
  preferred 决定 ⇒ 左 pitch 204.2、右 pitch 94.6。头像 210 高，右侧每条只隔 94.6，
  头像互相叠 115px —— 这就是用户说的"rightchat 都挨在一块了"。
- **关键教训**：LayoutGroup 的 pitch 由"条目自身高度 + 容器 spacing"决定。
  条目高度是塌的时候，怎么调 padding/spacing 都没用，必须先让高度非 0。

修复（commit efa4d44e0，脚本 `.workbuddy/tools/fix_rightchat_item_height.py`）：
- bg LayoutElement `ignore 1→0`，并显式写 `m_PreferredWidth: 690 / m_PreferredHeight: 136`。
  ⚠️ preferred 留 -1 时 `LayoutUtility.GetLayoutProperty` 返回 0，气泡宽度会塌成 31。
- bg sizeDelta 674x140 → 690x136；root VLG padTop 0→30、spacing 41.6→-14.82；
  contentroot VLG align 0→2；头像组 y=-55.099976 / lv=-104.099976 / vip=-108.099976；
  content 右边缘 822、左边距 40、宽 631.7483、y=-96；time y=-48.5。
- 端到端验证（挂机面板 chat 里塞 3 左 3 右）：全部 h=161.18，逐条间隙 43.00。

- 现象：Jenkins 打包目录（TimeSpaceGirl1-build）出的 APK 全是 848~855M，
  而开发目录出的包是 459M。用户问「怎么这么大都有 1G 了」。
- **根因**：`FileUtils.CopyDir`（`Assets/Scripts/Core/Core/Utils/FileUtils.cs`）
  用 `Directory.GetFiles(fromDir)` 拷文件，macOS 上该 API 返回 `.filename.XXXXXX`
  形式的 Unity atomic-write 临时文件。这些临时文件随 `CopyAssetBundleToStreamingAssets()`
  进了 StreamingAssets，又随 `BuildPipeline.BuildPlayer()` 打进 APK。
- 实测：打包目录最新 APK 有 6160 个文件（vs 正常 3193），其中 2742 个是 `. 前缀`临时文件，
  冗余 416MB。每个正式 AB 文件都有一个同大小的临时副本。
- 开发目录不受影响：那里的 AB 是 GUI 手工打的，StreamingAssets 里没有临时文件残留。
- **修复（commit 47fdf5e30，已推 release）**：
  1. `FileUtils.CopyDir`：跳过 `.` 前缀文件/目录（C# 层根治）
  2. `build_apk.sh` / `aab_release.sh`：Unity 构建前 `find -delete` 清理 StreamingAssets（兜底）
  3. `resource_build.sh`：AB 重建后清理 StreamingAssets（兜底）
