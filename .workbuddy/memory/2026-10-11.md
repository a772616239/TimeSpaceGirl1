核验过程与证据：

- 干扰项排除：Homebrew 的 3 个 mongodb plist 都不是实际数据源 —— `homebrew.mxcl.mongodb-community` 已加载但 `exit 48`（端口被占）；`@4.4` 是僵尸注册（文件已移入 `_backlog`/`_backup`）；`@7.0` 未加载。
- 磁盘常驻项全部在位：`/home/java` 软链、`/etc/auto_master` 的 `#/home auto_home` 仍注释、ssh 私钥、各二进制。
- 端到端复测：本地 :16081 / :6479 可连；云服 :16181 TCP 握手成功、ss 显示 7700+16181 LISTEN、`ts-frps` active；frpc `start proxy success`（00:10:53）。
- 自愈实证：00:10–00:11 一次网络抖动，frpc 自动重登、token-sync 2s 重连 ⇒ 登录瞬间网络未就绪可自愈。

**两个误导点记一笔（避免下次误判）**：
1. `curl http://云服:16181/` 返回 `000` 且耗满超时 → **不是隧道坏了**，是游戏服是 netty 私有协议、不认 HTTP。判隧道要用 TCP 握手 + frpc 注册日志。

## 「为什么延迟这么低」——实测澄清 + 纠正我自己的测量错误

**结论：它不是延迟低，是只跨了一次 WAN。物理单向 ~150ms 一分省不掉。**

| 指标 | 实测 |
|---|---|
| 到云服 RTT（常驻通道逐行打点） | 239–804ms，**中位 299ms**（抖动 3.4×） |
| 镜像端到端（生产写→本地可见，5 连测） | 251/257/264/282/315ms，**中位 ≈264ms** |
| 理论单向 | ≈150ms |
| 玩家视角 RTT | ≈600ms（= 2× 单向，因为多了一次隧道跳） |

**我上一轮的两个测量错误（必须更正）**：
1. `curl %{time_connect}` 到云服 = 1.6ms、到 1.1.1.1 = 1.3ms → 物理上不可能。真因：本机有**网络层透明代理**（系统代理 `127.0.0.1:7890` + 沙箱 `127.0.0.1:58555` + `utun0`–`utun4`），TCP 握手在本地就被接走了。⇒ **所有 connect 类数字作废**（`--noproxy '*'` 也无效）。
2. 我据 `ssh gs true` ≈ 500–1600ms 推出「单程 245ms」——那 500ms 是**本机 load 12–14 下的进程启动 + 密钥交换开销**，不是链路。数字凑巧接近，但推理是错的。
3. `traceroute` 被系统拦（operation not permitted），无法做路由取证。

**可信方法**：`ssh -M -o ControlPath -fNT gs` 建常驻主连接 → 远端 `cat` → python 逐行打点，无远程 fork、无连接建立开销。

**四个"便宜"的结构性原因**：① 只跨半程（单向）；② 常驻长连接（frpc↔frps 的 TLS、token-sync 的 SSH 建好不拆）→ 无握手/鉴权开销；③ keyspace 事件推送 → 无轮询量化误差；④ 游戏服在本机 → 服务端处理≈0。

**代价**：玩家 RTT 翻倍（≈600ms），比把服直接开在云上多一整趟 WAN —— 这是内测级的硬限制之一。已写入 `REF-shard10002.md` 新增「延迟画像与测量纪律」一节。
