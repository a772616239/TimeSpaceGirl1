## 🔴 事故 2（更正事故 1 的归因）：`go` 账号变新号 —— 客户端 Google 登录 SDK 被换，账号 id 形态变了

### 账号名是怎么算出来的（链路已逐层证实）
```

  → GoogleSignMgr.cs:26  按 platformId 取不同 SDK 的 id
      platformId==1 (Google)  → GetAcc("go" + id)      // 真机=PlayGames, 非真机=SignInSample
```

2. ⇒ **`protobuf` 拿到的不是模块表而是 `boolean`**。本机复刻错误消息形态一致（本地带调试信息会多 `local 'protobuf'`，strip 后正好只剩 `a boolean value`）。
3. **机制**：`require` 在 `package.loaded[require名]` 里查值；`module(name)` 只写 `package.loaded[name]`。
   chunk 跑完后若 `package.loaded[require名]` 仍是哨兵，Lua 会把它填成 **`true`** ⇒ **require 返回 `boolean true`**。
   实测（`LuaEncoder/luajit_mac/64/luajit`，2.1.0-beta3）：
   - searcher 返回**空 chunk** ⇒ `require "protobuf/protobuf"` 返回 **boolean**
   - 真正加载 `protobuf_protobuf_64.bytes` ⇒ 返回 **table**
   - LuaJIT 会把 `/` **归一化成 `.`** 当 `package.loaded` 键（实测有 `loaded["protobuf.protobuf"]`、无 `loaded["protobuf/protobuf"]`）
   - `require "Message/CommonProto_pb"` 因 `module` 声明是**短名** ⇒ **恒返回 `boolean true`**

### 结构隐患（真凶温床）
- `protobuf/protobuf.lua:39` → `module("protobuf.protobuf")`（点号全名）
- 30+ 个 `~Lua/Message/*_pb.lua:2` → `require "protobuf/protobuf"`（**斜杠**）⇒ 只有归一化生效时才对得上
- `~Lua/Message/CommonProto_pb.lua:3` → `module('CommonProto_pb')`（**短名**）vs 外部 `require "Message/CommonProto_pb"` ⇒ **永远不匹配**

## 13:00–13:15 验证「服务端改动是否影响线上玩家」→ 顺带查出部署脚本的假成功缺陷

**触发**：用户问「服务器端改的能兼容生产服吧，不影响线上玩家？」——不能凭印象答，逐层取证。

**结论：兼容，唯一可感知影响是部署那一刻的秒级重载窗口。**

**① 响应内容层（对生产库只读 dry-run 已验）**
- 新字段按需下发，只有中文 `name` 的老记录响应体**逐字节不变**。

  ⇒ 新字段是死键，不会被渲染也不会被误用。
- 服务端 `putIfNotEmpty` 只读 Mongo 文档写进新响应对象，**不回写 DB**；Redis 调用全是读。
- 调用方清单：线上 `localhost_access_log` 里 `/tk/*` 只有 5 个端点
  （`getNotice` 97 / `getServerList` 42 / `userLogin` 35 / `getUserInfo` 29 / `registerUser` 22，当日 366 次总量），
  全来自游戏客户端，**没有 Web 端或第三方**。

**② 流量量化（近 7 日 `localhost_access_log`）**
- `getServerList` 日调用量 2 / 2 / 1 / 1 / 55 / 11 / 42；**单小时峰值 14 次**（10-12 10时、10-10 16时）。

- ⇒ 秒级窗口撞上请求的概率 < 1%，失败表现 = 登录请求失败一次、重试即可。

**③ 🔴 发现并修正部署脚本的「假报成功」缺陷**
原 `deploy` 流程是 `touch web.xml` → 立刻轮询接口 200 就算成功。**这是错的**：
- 上传 `.class` **不会**触发重载（`WEB-INF/classes/**` 不是被监视资源）；
- `touch web.xml` 触发的重载**有 20~40s 延迟**，而重载前旧 class 照样返回 200
  ⇒ 轮询会**在重载发生前就返回成功**，然后「没发现 name_en 字段」还被当成正常（因为数据没写）。
- 已改为：轮询 `catalina.out` 的 `HostConfig.reload` + `[/tk]` 行（**非本地化字串**，中英 Tomcat 通用）
  作为重载判据，≤120s；未观察到则还原磁盘 class 并报错。

**④ 沙箱实证（本机完整 Tomcat 8.5.95，`/tmp/tclab`，端口 18080，dummy.war）**

| 动作 | 结果 |
|---|---|
| 改 `WEB-INF/classes/**` | ❌ 不触发重载 |
| `touch WEB-INF/web.xml` | ✅ `HostConfig.reload` → `context.reload()`；**只重载该应用、不重新解包**；空应用 **17ms**；补丁保留 |
| `touch <app>.war` | 🔴 `undeploy` + 重新解包 ⇒ **补丁被覆盖回原版**（实测 marker 从 PATCHED_V3 变回 FROM_WAR） |

- 压测：持续请求 1110 次、期间 6 次重载、**全部 200**（空应用）。
- 代码依据：`lib/catalina.jar` 的 `HostConfig.checkResources()` 两条通路 ——
  `redeployResources`（`.war`/`context.xml` ⇒ undeploy+重新部署）vs
  `reloadResources`（`context.findWatchedResources()` ⇒ 只 `context.reload()`）；web.xml 属后者。
- ⚠️ 真机窗口比沙箱大：同应用**冷部署实测 3,809ms**（TLD/JAR 扫描 ~2.87s +
  `WebContextListener`/Mongo 池 ~0.56s），reload 省解包但省不掉这两项 ⇒ **秒级**。
- ⚠️ 线上 `catalina.out` 里 `/tk` 重载次数基线 = **0**：该登录服**从未热重载过**，历史都是整机重启
  （最近进程启动 10-Oct 17:22:56，`Server startup in 7605 ms`）。本次是首次用此机制。
