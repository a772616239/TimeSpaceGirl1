## 4. 根因链条（为什么玩家能打到 GM 指令）

### 4.1 漏洞点：调试控制台绑在公网游戏协议上

`GMRequestHandler` 是标准 `@Component` + `BaseHandler`，注册在**玩家客户端协议表**里：

```java
// GMRequestHandler.java:69-78
public MessageTypeProto.MessageType getMessageCode() {
    return MessageTypeProto.MessageType.GM_REQUEST;      // 10606，走 16081 游戏端口
}
public void processWithProto(ISession iSession, CommonProto.GMCommand gmCommand) throws Exception {
    if (!GameApplication.serverProperties.isDebug()) {
        throw new ErrorCodeException("In a formal setting");   // 唯一闸门
    }
    ...
}
```

即：**鉴权只有一个布尔值**，没有白名单账号、没有 IP 校验、没有二次口令、没有速率限制。

### 4.2 闸门当时是开的（有运维注释为证）

- 10-10 时的外部配置 `config/application.properties`（备份 `application.properties.bak.20261010180623`）**只有两条 Mongo URI，没有 `server.debug`**。
- 当时线上 jar 内置的 `application.properties` 中该键为 `true`；外部文件不覆盖该键 ⇒ Spring 绑定结果为 **true**。
- 10-18 01:10 外部配置被补上一行，备份 `application.properties.bak.20261018011132` 里留着当时的原话：

```
# 2026-10-18 关闭 GM 调试通道（覆盖 jar 内置 true）
server.debug=false
```

⇒ 10-10 00:00 至 10-18 01:10 之间，**任何玩家只要发 `GM_REQUEST` 就等于 GM**。

### 4.3 这条通道能干什么（最坏影响面，`GlobalGm.java` 常量表）

| 指令 | 编号 | 效果 |
|---|---|---|
| `ADD_ITEM` | 1 | `1#<itemId>#<num>` 任意道具任意数量 |
| `ADD_CARD` | 2 | 任意英雄卡 |
| **`HERO_STAR`** | **4** | **`4#<heroId>#<star>` 直接产出指定星级英雄（本次被用的就是它）** |
| `ONE_KEY_ITEM_OR_HERO` | 6 | 一键发放**全部**道具各 9999 + 全部英雄卡 |
| `FULL_OF` | 21 | 一键全满：队伍英雄满星满级 + 科技树满级 + 异妖全解锁 |
| `ADOPT_ALL_DIFFICULTY` | 19 | 一键通关全部主线 |
| `VIP_LEVEL` | 16 | 任意 VIP 等级 |
| **`GM_LOGIN_BY_UID`** | **40** | **给任意 uid 签发登录 token，直接顶号** |

`GM_LOGIN_BY_UID` 意味着当时**任意玩家可以接管任意账号**，这比刷资源严重一个量级（`GMRequestHandler.java:500-519`）。

## 5. 检测盲点（为什么 `cheat_scan.py` 判了 CLEAN）

现有扫描对 10000224 的输出是「✅ 未发现作弊证据」，这是**假阴性**，三个原因：

1. **无 `heroLog`**：`HERO_STAR` / `FULL_OF` / `Cmd_addhero` 改星级和等级时**不写 `heroLog`**（`heroLog` 只在 `upHeroLevel` / `upHeroStar` 里写，见 `HeroLogic.java:1332`）。所以 48 次满星在任何"英雄养成日志"里都看不到。
2. **无 `itemLog`**：`m5_x1_game_10001.itemLog` 里该号 0 条（同期 10000221–10000225 全为 0；10000227 起才正常有 12 条）。`cheat_scan` 的"核心货币对账"在空日志上是**恒闭合**的，等于没校验。
3. **判据缺阈值**：脚本把"50 个英雄 / 最高 13 星 340 级"当普通养成信息打印，没有和 `maxRank`、`openLevel`、同级分位数做对比，也没检查 `reason=28`。

> 补充：BI 文件流水（`assets/log/jl_item`）保留期远长于 Mongo `itemLog`，本次取证完全靠它。服务端 `logback` 的 `gameserver.log` 只保留约 3 天（现存最早 10-19），已无法回溯 10-10。

## 6. 修复建议（按成本-收益排序）

### P0（今天就做，纯服务端改动，无需发版客户端）

1. **把 GM 通道从生产 handler 表里摘掉**，不要只依赖 `server.debug`：
   - 最小改动：`GMRequestHandler` 加 `@Profile("dev")` 或 `@ConditionalOnProperty(name="server.debug", havingValue="true")`，让它压根不注册；
   - 或直接删掉 `getMessageCode()` 的 `GM_REQUEST` 映射，GM 只走服务端 thrift（`127.0.0.1:7916`）。
2. **删掉两处地雷**：`config/logicSrv.properties` 的 `server.debug = true` 改为 false 或删除该文件；jar 打包模板里的 `application11/12.properties`（debug=true）改为 false 或从产物中剔除。
3. **加启动自检**：服务启动时若 `isDebug()==true` 且 `server.id` 是正式区服，直接 `System.exit` + 告警，而不是静默开放。
4. **处置数据**：10000224 的 48 个 13★/340 英雄（模板 10001–10079）删除或回退到 `star=4 / level=1`，`maxForce` 重算；10000248 封禁 + 拉黑其 VPN 段。

### P1（本周）

5. **GM 操作审计落库**：`HERO_STAR`/`FULL_OF`/`ONE_KEY_*`/`GM_LOGIN_BY_UID` 一律写独立集合（操作者 uid、目标 uid、指令原文、时间、IP），并写 `heroLog`。
6. **修 `itemLog` 断档**：排查 `ItemLogic.addItemLog` 的异步队列在 10000221–10000225 这段为何整体丢失（疑似队列 flush/降级），否则一切"收支对账"都不可信。
7. **`cheat_scan.py` 补三条硬信号**：
   - `hero.level > openLevel(hero.star)` 或 `star == maxRank` 的英雄数 ≥ N；
   - 同级/同建号日分位数（本例：maxHeroLv 340 vs 同级 P100=26）；
   - 从 `assets/log/jl_item/<date>` 反查 `reason=28`（`GM_REWARD`），而不是只查 Mongo `itemLog`。

### P2（设计层）

8. 客户端可控数值一律在入口收敛：`Hero.upStar(int)` 是裸 `star += n`、`Hero.setLevel` 无上限（`Hero.java:186/196`），校验全散落在各 handler；建议在实体层加断言，越界即抛错并告警。
9. `UpHeroLevelHandler` 的 `targetLevel` 仅在 `breakId != 0` 时校验上限（`HeroLogic.java:1283-1295`），走"升级"分支时没有任何硬上限，靠遍历配置表兜底 —— 建议补 `targetLevel <= maxOpenLevel`。
10. `ExpeditionLogic.createHero` 里 `int star = hero.getLevel()` 把等级当星级用、并把 `finalstar`（下限 50）写进 `level`（`ExpeditionLogic.java:820-838`），语义错位且是"等级放大器"，建议单独评审。
