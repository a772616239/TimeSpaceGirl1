## 二、四道闸门，全部关闭

### 闸门 1：客户端看到的礼包列表 = 服务端下发的，不是全表

`BuyGoodsLogic.getGoodsBagInfo(uid, list)`（`BuyGoodsLogic.java:1864-1936`）只遍历玩家身上的四种包：

```java
for (bag : rechargeInfo.getPerpetualMap().values()) // otype=1 永久
for (bag : rechargeInfo.getTimeLimitMap().values()) // otype=2 活动
for (bag : rechargeInfo.getReceiveMap().values())   // otype=3 领取
for (bag : rechargeInfo.getPushMap().values())      // otype=4 推送
```

客户端 `ShopManager.lua:668` 用 `GetRechargeItemInfo(id)` 按这个 id 取配置，**没有**「遍历全表按 ShowType 铺货架」的路径（整个 Lua 侧没有对 ShowType 的过滤代码）。

### 闸门 2：otype=4 的包只能在 `createPushBag` 里生成，入口由 `PackPush.Packs` 决定

`refreshWelfareState`（`BuyGoodsLogic.java:2013`）明确跳过推送型：

```java
if (entry.getValue().getOtype() != RechargeType.push.getType()) { // 推送不在此初始化
```

推送型唯一来源是 `createPushBag`（`:2701`），而它的 bagId 只来自 `PackPush.Packs` 列：

```java
List<SPackPushConfig> list = SPackPushConfig.findConfigByCon(type, star, activityList);
...
boolean tempPush = createPushBag(bagId, user, num, con.getId());   // :2490
```

实测 `PackPush`（71 条）引用 67 个礼包 id，**全部落在 30500~36016 段**，13 个老 id 一个都没出现：

```
Packs 列出现的 id 区间: 30500 ~ 36016
21 / 24 / 25 / 26 / 27 / 28 / 29 / 30 / 31 / 32 / 400 / 401 / 402  → 出现 0 次
```

### 闸门 3：上架条件等级 999–999，`judgeOpen` 永不成立

`OnSaleRule` 被服务端解析成 `condition`（`SRechargeCommodityConfig.initConditon`，`:158`），`judgeOpen` 对 `con[0]=="1"` 的判定是：

```java
if (con[0].equals("1")) {           // 玩家等级
    int level = ...getLevel();
    if (Integer.parseInt(con[1]) <= level && level <= Integer.parseInt(con[2])) { ... }
}
```

`1#999#999` ⇒ 要求等级落在 [999, 999]，正常玩家不可能满足。24~32 还额外把时间窗钉死在 2021-01-01。

### 闸门 4：`ChannelRechargeIdConfig` 里没有计费点

支付走的不是 `RechargeId`（全表 833 行该字段本来就全为空），而是 `ChannelRechargeIdConfig`，以**礼包 Id** 为键映射各渠道计费点。这 13 个 id 在各渠道列上**全部为空**：

```
id=21/24/25/26/27/28/29/30/31/32/400/401/402  → 计费点 ''（无）
```

即使前面三道被打开，SDK 侧也发不出付费请求。

## 三、关于 `Limit=0`：对推送型礼包根本不生效

`Limit` 的注释是「0 为无限次」，看着吓人，但 `otype=4` 的限购是在生成时被覆盖的：

```java
AbstractWelfareBag bag = initUnitWF(user, config);
if (num != 0 && num + hasOpen > info.FIVESTARLIMIT) bag.setLimit(info.FIVESTARLIMIT - hasOpen);
else if (bag != null) bag.setLimit(num);          // ← num 来自 PackPush 的推送次数
```

`buildGoodsInfo` 读的也是 `bag.getLimit()`，不是配置的 `Limit`。所以这批行的 `Limit=0` 是**死字段**。

顺带说明：全表 `Limit=0` 共 141 个，其中 117 个是 `ShowType=8`（含 67 个现役推送礼包）。现役那批的限购同样由 `createPushBag` 覆盖，不存在「无限刷」。

## 四、为什么不删行

服务端代码里把这几个 id **硬编码**了：

```java
// BuyGoodsLogic.java:2688
public static boolean isFiveStarBag(int id) {
    if (id == 21 || id == 400 || id == 401 || id == 402) return true;
    if (id >= 7300 && id <= 7304) return true;
    if (SPackPushConfig.isPushGift(id)) return true;
```

一旦有人（或某条推送配置）用这些 id 调 `createPushBag`，`getConfigById` 会返回 null，`initUnitWF` 内部 try/catch 吞掉 NPE 返回 null，紧接着 `:2723` 的 `bag.setLimit(...)` **没有 null 保护** ⇒ 直接空指针。删行的收益是 0（本来就是死行），风险是给未来埋一颗雷。

## 五、真正值得上报的问题

**「五星成长礼」这套老编号整体没接线。** 证据：

- `isFiveStarBag` 硬编码 21/400/401/402 + 7300~7304，说明设计上它是活功能；
- 但 `PackPush.Packs` 里 7xxx 段**一个都没有**（全部是 30xxx~36xxx）；
- 13 个老 id 的计费点全空 ⇒ 渠道侧也没给它们开过商品。

也就是说：**这 13 行 + 7300~7304 是 2021 年那版「星级成长礼」的残骸，现在跑的是 3xxxx 段的新版。** 老版从未在线上生效，不需要下线动作；如果产品确认不要了，正确做法是连同 `isFiveStarBag` 的硬编码一起清理（代码 + 配置一起改），而不是单独删表行。
