## 一、「皮肤礼包」到底是什么

`RechargeCommodityConfig` 的 `ShowType` 列第 4 行有官方注释：`27、皮肤礼包`。查完实际配置后结论如下。

### 1. 表里只有 3 个 SKU，名字叫「废弃」

| 礼包 Id | 价格 | Name / Desc / Tip | 语言值 | Limit |
|---|---|---|---|---|
| 8000 | 648 元 | 34010001 | **废弃** | 1 |
| 8001 | 648 元 | 34010001 | **废弃** | 1 |
| 8003 | 648 元 | 34010001 | **废弃** | 1 |

三行的 `Name`、`Desc`、`Tip` 全部指向同一个语言 id，而 `Language.txt` 里 `34010001` 的值就是两个字：`废弃`。

### 2. 游戏里没有皮肤系统

| 检查项 | 结果 |
|---|---|
| `Language.txt` 搜「皮肤」 | **0 条** |
| `Language.txt` 搜「外观」「衣橱」 | **0 条**（只有「头像框」43 条） |
| 客户端 `GlobalDefine.lua:2652` `DirectBuyType` | 只定义 11–17（限时豪礼…极速探索特权），**无 27** |
| `StoreTypeConfig` 的 Id / StoreType | **无 27**，也没有对应商店页签 |

结论：这个货架**从未实现**，没有 UI 入口，玩家看不到也买不到。它不是“缺皮肤道具”，而是配置残留。

### 3. 上一轮的错误说法已撤回

上一轮报告写的是「皮肤礼包 3 个还是没皮肤，缺皮肤道具 id」——这个判断是错的。不存在“皮肤道具 id”，因为整块功能没做。

同样撤回的还有一条：曾依据 `OnSaleRule='1#999#999|4#0#0'` 推断「等级 999 锁死 ⇒ 283 个 SKU 不可见、上一轮改造的 179/180 无效」。该推断**不成立**——导出的 `Config/Data/RechargeCommodityConfig.lua` 的 `__fields` 里根本没有 `OnSaleRule`，客户端无法据此过滤；服务端 java 也没有任何 `RechargeCommodity` 引用。`OnSaleRule` 的真实语义**至今未核实**，不能再当判据。

| 8003 | `16#7452\|4#11100` → `16#7452` | `废弃` → `后续开放` |

### C. 星级成长礼 13 个早期遗留行改名

`21, 24, 25, 26, 27, 28, 29, 30, 31, 32, 400, 401, 402`

这 13 行的特征：`Otype=4`、`PosterUiId` 为空、内容完整（钻+金币+钱+经验）、**`Limit=0`（无限次购买）**，名字却是「废弃」。

星级归属无法从配置判出（`LoginPosterConfig.ShopId` 全空），因此**不改内容、不编造星级名**，统一改成中性占位「后续开放」。真实星级名需产品确认后再定。

## 五、必须知道的三件事

**1. 上一轮的「礼包内容改造 +11.2% 收入」结论要打折看。**
精确核算：上一轮改过 `BaseReward` 的包共 **177 个**，其中 **160 个名字至今仍是「废弃」**，只有 17 个在本轮修好。这 160 个集中在：

| 货架 | 改过内容但名字仍「废弃」 |
|---|---|
| 限时商市 (ShowType=22) | 116 |
| 珍奇宝阁 (ShowType=23) | 44 |

如果这两个货架对玩家可见，那批内容改造“加了紫晶卡”的效果，会被货架上的「废弃」两个字直接抵消。要验证上一轮的收益结论，得先把这 160 个名字修掉。

**2. 拍脸推送链路其实没有命中「废弃」。**
`PatFaceManager.SetPatFaceDaqta`（`Modules/Expert/PatFaceManager.lua:434-482`）要求 `PosterUiId` 非空才入队：

```lua
if curRechargeCommodityConfig and curRechargeCommodityConfig.PosterUiId then
```

而 `PosterUiId` 非空的 152 个包（全部在星级成长礼货架），名字**一个都不是「废弃」**（0/152）。所以「弹出『恭喜你激活了废弃』」这个场景，在客户端主动拍脸路径上不会发生。

真正会用 `Name` 拼文案的是 `IndicationManager.lua:849-850` 的后端推送路径：

```lua
local name = ...RechargeCommodityConfig, msg.id[#msg.id]).Name
local title = string.format(GetLanguageStrById(50168), GetLanguageStrById(name))
-- 50168 = "恭喜你激活了%s,是否前往购买？"
```

这条路径推什么包由**服务端**决定，服务端源码不在本仓库，无法确认。所以本轮改名是「消除隐患」，不是「修复已知线上事故」。

**3. 星级成长礼那 13 个包的 `Limit=0` 值得单独查。**
`Limit` 的官方注释是「商品购买次数（0 为无限次）」。这 13 行内容完整、无限次购买、名字却是「废弃」。如果它们在线上真的可买，那是比改名更严重的问题。建议产品确认这 13 行是否该直接下线。
