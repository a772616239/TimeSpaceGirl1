> 适用范围：`scripts/table_sync.py --targets gs` 的 23 张可推表逐列核对。

> 结论先行：**23 张里只有 4 张属于「推了等于没推或只是修正」，其余都会改变线上数值/付费/开放节奏。**

语义漂移 29 张，其中 6 张结构红灯（`ROW_LOSS` / `COL_LOSS` / `HEADER_DIFF` / `REVIEW`）永不推，

## A 组：同值不同写法（推了等于没推，2 张）

只是浮点表示法/精度不同，**数值完全相同**。推上去唯一效果是把线上文件换成另一种写法。

| 表 | 列 | 本地 | 线上 | 判定 |
|---|---|---|---|---|
| `ExchangeRate` | `Price_6`（float） | `15.92` | `15.920000000000002` | 同值 |
| `GuildSetting` | `ForceScore`（float） | `1E-3` | `0.001` | 同值 |

> ⚠️ `GuildSetting` 的 `1E-3` 是科学计数法。服务端按 `Double.parseDouble` 解析没问题，
> 但如果有任何地方用 `Integer.parseInt` 或字符串比较，会出问题。建议本地写回 `0.001` 更稳。

---

## B 组：空值补默认 0（口径变化，2 张）

导出器 `GetValByDefault` 现在把数值列空值写成 `0`（2026-10-21 从 `nil` 改 `null` 之后的连带效果），
线上老数据是 `null` 或空串。

| 表 | 列 | 本地 | 线上 | 影响 |
|---|---|---|---|---|
| `HeroStarBackConfig` | `BackStar`（Int，15 行全变） | `0` | `null` | 服务端 `parseFiledInt("null")` → 空数组；`"0"` → `[0]` |
| `MonthcardConfig` | `Time`（int，2 行全变） | `0` | 空串 | 同上 |

**这一组不是「数据变了」，是「空值表示法变了」。** 需要确认服务端这两个字段的用法：
如果代码是 `arr.length == 0 ? 默认值 : arr[0]`，那么 `[0]` 会让默认值失效 —— 属于隐性 bug。
推之前建议在测试服上确认这两个字段的实际行为（测试服现在已经是 `0` 了）。

## D 组：奖励/付费内容变更（高危，8 张）

**这一组会直接改变线上玩家的收益和付费行为。** 除 `ChannelConfig` 外都需要产品确认「这是不是已经该上线」。

| 表 | 列 | 变动 | 样例（线上 → 本地） | 风险 |
|---|---|---|---|---|
| `StoreConfig` | `OpenLv`（`mut,int#int,1`） | 11 格 | `7911: 95#999 → 1#999` | 🔴 **开放等级 95 → 1**，等于全服提前开放这批商品 |
| `RechargeCommodityConfig` | `RewardShow` 782 / `BaseReward` 776 / `OnSaleRule` 39 | 1670 格 | `2: 16#300 → 16#330`；`OnSaleRule 102: 3#601\|4#0#0 → 1#999#999` | 🔴 **充值商品奖励 +10%**，上架规则也变了 |
| `VipLevelConfig` | `VipBoxDailyReward` | 19 行全变 | `0: 16#1\|60#1 → 16#10\|60#1` | 🔴 VIP 每日宝箱奖励 ×10 |
| `VipLevelConfigNew` | `VipBoxDailyReward` | 18 行全变 | `1: 16#20\|60#1 → 16#60\|60#1` | 🔴 同上 |
| `MainLevelConfig` | `RandomReward` | **2540 行** | `1012: 20002#1#2000 → 20002#20001#` | 🔴 每关随机奖励整体重配，且新格式末尾空值 |
| `RewardGroup` | `RewardItem` | 320 格 + 3 新行 | `205680: 3030681#3025 → 3030681#3025` | 🔴 奖励组整段重配 |
| `LuckyCatConfig` | `ValueUp` / `ValueDown` | 32 行 × 2 列 = 64 格 | `1: 308 → 99`、`185 → 88` | 🔴 招财猫产出曲线全变 |
| `MonthcardConfig` | `Price` | 1 格 | `1: 30 → 12` | 🔴 **月卡价格 30 → 12** |

> `MainLevelConfig` 的 `20002#1#2000 → 20002#20001#` 尤其要小心：不只是数值变了，
> 三段式的**段数结构**也变了（`#1#2000` 变成 `#20001#`）。这种改动如果服务端解析器没同步升级，
> 会静默解析成 0 个奖励。
>
> `RechargeCommodityConfig` 还多一列 `SystemMessageShow`（`COL_GAIN`）——服务端
> `STableManager` 是按字段名反射注入的，`SRechargeCommodityConfig` 里没有这个字段的话，
> 要么被忽略、要么抛异常。**推之前必须确认服务端已有该字段。**

## F 组：结构红灯，永不推（6 张）

| 表 | 判定 | 原因 |
|---|---|---|
| `EncourageTaskConfig` | `ROW_LOSS` | 线上多 25 行（`16001~16025`），覆盖会删掉线上任务 |
| `EncouragePlanConfig` | `ROW_LOSS` | 线上多 1 行（`16`） |
| `MultiLanguage` | `ROW_LOSS` | 线上多 1 行（`10301`） |
| `Language` | `COL_LOSS` | 线上 5 列含 `Korean`，导出只有 4 列 → 韩语全空 |
| `ChannelRechargeIdConfig` | `HEADER_DIFF` | 本地少 `Android_99_Child2`，覆盖会串列 |
| `RewardItemConfig` | `REVIEW` | 本地多 103 个 `990000+` 未发布道具 |

这 6 张的根因都在**导出器/源表**，不在同步工具：

- `Language.txt` 缺 `Korean`：导出器没把这个语言列写出去，改 `DataToTxtExporter` 才能解决；
- `EncourageTaskConfig` / `EncouragePlanConfig` / `MultiLanguage`：线上有的行源表里没有
  （线上手工加过或从别的分支同步过），需要先把这 26 行补回源表；
- `ChannelRechargeIdConfig`：源表少一个渠道列；
- `RewardItemConfig`：103 个未发布道具要不要上线，是产品决策。

## 建议的推送顺序

1. **A 组先推**（2 张，零风险），顺手把 `GuildSetting.ForceScore` 的 `1E-3` 改成 `0.001`；
2. **B 组先查服务端语义**，确认 `null` 和 `0` 在这两个字段上的行为差异，再决定推不推；
3. **C 组逐表抽查**（尤其 `ArenaRobotConfig` 的名字 id 整体 -1），确认是有意调整后推；
4. **D 组必须产品确认**，且 `RechargeCommodityConfig` / `SkillLogicConfig` 要先确认服务端已有新字段；
5. **F 组**按上面列的根因逐个修源表/导出器，修完重新体检。

## 怎么执行

```bash
# 只推 A 组
python3 scripts/table_sync.py --apply --targets gs --only ExchangeRate,GuildSetting --yes

# 只推 C 组
python3 scripts/table_sync.py --apply --targets gs --only SupremacyLevelConfig,MonsterConfig,CombatControl \
  --only CampWarRewardConfig,DialRewardConfig,LotteryRewardConfig,MotherShipConfig,LuxuryFund,ArenaRobotConfig --yes

# 推完重启（会踢线）
python3 scripts/table_sync.py --apply --targets gs --only ... --restart --yes
```

> `--only` 会忽略基线、点名推送，但仍然过体检：`PARSE_BAD` / `NIL_CELLS` 等红灯照样拦。
